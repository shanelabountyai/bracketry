# 07 — Decision log: Bracketry

**Status:** D-1 to D-20 recorded 2026-10-05 with the starter (L-000).
**Precedence:** this log amends the PRDs. Where they conflict, this log wins. Treat each row as settled; append new decisions with new numbers and never change a settled row's meaning.

| # | Topic | Decision | What it means for the build |
|---|---|---|---|
| D-1 | Stack | **Clone `saas-foundation` at its latest tag.** Single Next app, no monorepo. | Next.js 16, Prisma 7, Postgres 17, zod, Vitest, Playwright, as shipped by the template (read at v1.2.0 in the Callboard clone; use whatever tag is current). Template-owned paths are never edited; `npm run foundation:drift` is part of the gate. Domain code goes in `src/lib/league/` (pure) and `src/app/o/[org]/…` (routes); tables in `prisma/schema/bracketry.prisma`. |
| D-2 | Solver or heuristic | **Heuristic: greedy draft, score, repair by local search.** No OR-tools, no ILP, no SAT. | The lesson is modelling constraints and reporting a heuristic's result without overclaiming. The seam for a real solver is `scoreSchedule`: a solver would replace `repair` and still be judged by the same function. Do not add a solver dependency. |
| D-3 | Determinism | **Same inputs + same seed → same schedule.** | `src/lib/league` never calls `Math.random`, `Date.now`, `new Date()` or reads the timezone; a lint rule enforces it (L-002). Randomness is `mulberry32(seed)`. Iteration over maps and sets must be in a defined order (sort keys). Each schedule version stores its seed, an input hash and its fingerprint. |
| D-4 | One scoring function | **`scoreSchedule` is the only judge.** | The repair loop, the publish gate, the reschedule tool and the quality table all call it. No second implementation of any rule in SQL, in a component, or in a test helper. |
| D-5 | What the product claims | **Never "optimal". Report the work.** | Every run shows soft cost before and after, iterations, accepted moves. Where a floor is provable by counting, show it. Copy on every screen and in `WRITEUP.md` follows this. |
| D-6 | Dates and times | **Days are `CHAR(10)` strings, wall times `CHAR(5)`; one timezone per season.** No `@db.Date`. | Carried from Bookable, whose `CLAUDE.md` records a silent day shift through Postgres `date` → JS `Date`. The engine has no instants at all. "Today" is derived in one place from the injected clock and the season's timezone. |
| D-7 | Slot shape | **Uniform game length per season; start times on a shared grid.** | Two slots overlap only when day and start match. Variable-length games and travel time between fields are out of scope. |
| D-8 | Feasibility wording | **Necessary conditions only, stated as such.** | A pass reads "these inputs could fit". The generator may still return unplaced games, and the console handles that case as a normal outcome. |
| D-9 | Unplaced, never illegal | **The generator returns unplaced games before it returns a hard violation.** | An unpublishable result is a value, not an exception: the console shows what could not be placed and why. |
| D-10 | Schedule versions | **Append-only versions; publishing flips a pointer.** | A partial unique index allows one `published` version per season (hand-written SQL). Placements are never updated; a change is a new version. Superseded versions stay readable. |
| D-11 | Slot uniqueness | **The database refuses two games in one slot within a version.** | Unique (versionId, fieldSlotId) and unique (versionId, gameId). App code writes and maps the unique violation; it does not check-then-write. This is reuse of the Bookable/Reserve lesson, not a new one. |
| D-12 | Reschedule | **Minimal perturbation: only displaced games move.** | Tested game by game. "Regenerate the rest of the season" is a different action with its own warning (RAIN-05). |
| D-13 | Standings and results | **Results are append-only; standings are computed on read.** | A correction is a new `GameResult` row with `supersedesId`. No rank or total is stored as truth. A cache is allowed only with a verify path that recomputes and compares. |
| D-14 | Tiebreak chain | **An ordered list of steps in season settings. Not a rules engine.** | Five metrics, two scopes, restart or continue. Tied-scope steps are skipped until the group is balanced. An unbreakable tie is a shared rank until a commissioner records a decision. The system never draws at random. The config is versioned on the season. |
| D-15 | Brackets | **Single elimination, standard seeding, byes to top seeds.** | Seeding is a frozen snapshot with the standings fingerprint it came from. No ties. A result can be corrected until the next game in its line is played. Double elimination is P2. |
| D-16 | Who signs in | **League staff only.** | Commissioner = org owner or admin. Scorekeeper = org member, limited to results. Coaches, players and the public read public pages with no account. Use the foundation's authorization path; add permissions there the way the template documents, not ad hoc checks. |
| D-17 | Where generation runs | **Synchronously in a server action, with caps.** | At most 16 teams per division, 200 games per season, `maxIterations` ≤ 10,000. Basis: spec 01 §8. No job queue. If a real run in this repo exceeds 5 s, stop and raise it rather than adding infrastructure. |
| D-18 | Notices | **Through the foundation's notifications outbox, on publish only.** | Without provider keys every message is captured in the database. Declare the module required if code outside the marked lines imports it (`src/app/required-modules.ts`). |
| D-19 | Backlog ids | **`L-` numbers, continuous, never reused.** | Commits are `L-006: repair loop`. |
| D-20 | Pending suites | **The engine's suites ship as `tests/unit/league-*.pending.ts`.** | Vitest only collects `*.test.ts`, so CI stays green. An item starts by renaming its suite to `.test.ts` and watching it fail with `NotImplementedError`; it ends with that suite green. Do not weaken an assertion to pass it; if a fixture looks wrong, stop and raise it. |
| D-21 | Unplaced pinned game | **Listed as unplaced only; it does not score `PIN_MOVED`.** | `PIN_MOVED` is for a pinned game sitting in some other slot. A pinned game with no assignment entry is unplaced, which already blocks publishing, and D-9 keeps "unplaced" from ever being a hard violation. Decided by the owner at L-005 (2026-10-08). |
| D-22 | Manual tie resolutions | **The last logged decision listing exactly a group's teams wins; notes carry team ids.** | `manualResolutions` is read as an append-only log, so a correction is appended, never edited (as D-13). An entry listing any other set of teams does not apply. `StandingsRow.note` names teams by id because the engine has only ids; the screen swaps in names. A result naming a team outside `teams` is dropped for both sides. Confirmed by the owner in the L-008 restatement (2026-10-08). |
| D-23 | Rainout and the past | **The caller keeps past open slots out of the reschedule inventory; the engine has no clock.** | `reschedule` offers every free slot in the inventory, so an open slot before the rain day would be taken as a makeup (seen at L-010: a game rained out of Thu Apr 15 moved to Tue Apr 13). The caller drops open slots on or before the cut-off day and keeps every slot that holds a game. The capstone uses the rain day as the cut-off; L-017 uses today from the injected clock. Taken as the default at L-010 (2026-10-08) where the spec is silent; the owner confirms or replaces it at L-017. |
| D-24 | Engine slot ids | **The loader builds the engine's slot id as `day\|start\|fieldId`, never the row's UUID.** | `reschedule` orders displaced games by old slot id (open since L-007), which is calendar order only for ids of this shape. Unique (seasonId, day, start, fieldId) on `FieldSlot` makes the id one-to-one with the row inside a season, so no column is added. The loader lands with the first screen that calls the engine (L-013). Taken as a default at L-011 and shown to the owner in the plan (2026-10-08). |
| D-25 | Append-only and cascades | **The append-only triggers refuse a direct UPDATE or DELETE and let a foreign-key cascade through.** | `GameResult` and `TieResolution` share one trigger function; it returns early when `TG_OP = 'DELETE'` and `pg_trigger_depth() > 1`, which is true only inside a referential-integrity trigger. Without it the template's delete-org route fails for any org with a recorded score. `AuditEvent` needs no such line because it has no foreign keys. Chosen by the owner at L-011 (2026-10-08) over a strict trigger and over dropping the foreign keys. |
| D-26 | Constraints beyond §8 | **The database also enforces the result chain, pin and playoff slots, same-season joins and value shapes.** | One original result per game (partial unique), a result superseded at most once, and a correction must name a result of the same game: one linear chain, one current result. Unique `Pin.fieldSlotId`, `BracketGame.fieldSlotId` and `Bracket.divisionId` (regenerating a bracket deletes and recreates it). `Pin` and `Placement` carry `seasonId` with composite foreign keys, so a placement cannot join a version, game and slot from different seasons; `Team` carries `seasonId` for its unique name. CHECKs: day and time shape (CHAR(n) pads a short value rather than refusing it), legs, weekday, runs ≥ 0, home ≠ away, seed in uint32. `Season.status` is `setup` / `active` / `closed`. Chosen by the owner at L-011 (2026-10-08). |
| D-27 | Who may edit setup | **Season setup actions require `org.update` (owner and admin); no template edit.** | D-16 says commissioner = owner or admin, which `org.update` already is, so `src/core/authz/permissions.ts` stays untouched. The scorekeeper (org member, results only) needs a permission a member does not hold; that is a template-owned edit, so it is raised at L-015 rather than worked around here. Taken as a default at L-012. |
| D-28 | Generation console storage | **A run stores what the schema already has: the before-repair score rides inside `ScheduleVersion.report`, and `Game` rows are created at the first generation.** | `report` is the stored assignment's `ScoreReport` plus `before: { hardCount, unplaced, softCost }`, so the screen shows before and after with no new column. `Game` rows are written with `skipDuplicates` on (seasonId, key) inside the generating transaction; the engine input is always rebuilt from the current teams, so a team added after a first run changes the pairings of later runs while stored rows keep their first home/away (revisit before L-014 compares versions). A blank seed picks `randomInt(2^32)` in the action, never in the engine. Pins are not loaded yet; L-014 adds them to `buildInput`. |
| D-29 | Compare and pins | **Compare is by game key and slot identity: a game is "changed" when its stored placement differs, and a game placed in only one version shows as from or to "not placed". A pin is one `Pin` row; its legality is `scoreSchedule` over the existing pins plus the new one.** | Home and away come from the stored `Game` row (D-28), so compare shows who hosts as first stored, not as a later run would pair. A pin applies to the next generation; versions already made are never touched (D-10). Only a draft can be published; there is no republish of a superseded version (not in SCHED-02). Closed slots and games outside the current pairings are refused before scoring. |
