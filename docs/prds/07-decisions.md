# 07 — Decision log: Bracketry

**Status:** D-1 to D-20 recorded 2026-10-05 with the starter (L-000).
**Precedence:** this log amends the PRDs. Where they conflict, this log wins. Treat each row as settled; append new decisions with new numbers and never change a settled row's meaning.

| # | Topic | Decision | What it means for the build |
|---|---|---|---|
| D-1 | Stack | **Clone `saas-foundation` at its latest tag.** Single Next app, no monorepo. | Next.js 16, Prisma 7, Postgres 17, zod, Vitest, Playwright, as shipped by the template (read at v1.2.0 in the Callboard clone; use whatever tag is current). Template-owned paths are never edited; `npm run foundation:drift` is part of the gate. Domain code goes in `src/lib/league/` (pure) and `src/app/o/[org]/…` (routes); tables in `prisma/schema/bracketry.prisma`. |
| D-2 | Solver or heuristic | **Heuristic: greedy draft, score, repair by local search.** No OR-tools, no ILP, no SAT. | The lesson is modelling constraints and reporting a heuristic's result without overclaiming. The seam for a real solver is `scoreSchedule`: a solver would replace `repair` and still be judged by the same function. Do not add a solver dependency. |
| D-3 | Determinism | **Same inputs + same seed → same schedule.** | `src/lib/league` never calls `Math.random`, `Date.now`, `new Date()` or reads the timezone; a lint rule enforces it (L-002). Randomness is `mulberry32(seed)`. Iteration over maps and sets must be in a defined order (sort keys). Each schedule version stores its seed, an input hash and its fingerprint. |
| D-4 | One scoring function | **`scoreSchedule` is the only judge.** | The repair loop, the publish gate, the reschedule tool and the quality table all call it. No second implementation of any rule in SQL, in a component, or in a test helper. |
| D-5 | What the product claims | **Never "optimal". Report the work.** | Every run shows soft cost before and after, iterations, accepted moves. Where a floor is provable by counting, show it. Copy on every screen and in `WRITEUP.md` follows this. |
| D-6 | Dates and times | **Days are `CHAR(10)` strings, wall times `CHAR(5)`; one timezone per season.** No `@db.Date`. | Carried from Bookable, whose `CLAUDE.md` records a silent day shift through Postgres `date` → JS `Date`. The engine has no instants at all. "Today" is derived in one place from the injected clock and the season's timezone. |
| D-7 | Slot shape | **Uniform game length per season; start times on a shared grid.** | Two slots overlap only when day and start match. Variable-length games and travel time between fields are out of scope. |
| D-8 | Feasibility wording | **Necessary conditions only, stated as such.** | A pass reads "these inputs could fit". The generator may still return unplaced games, and the console handles that case as a normal outcome. |
| D-9 | Unplaced, never illegal | **The generator returns unplaced games before it returns a hard violation.** | An unpublishable result is a value, not an exception: the console shows what could not be placed and why. |
| D-10 | Schedule versions | **Append-only versions; publishing flips a pointer.** | A partial unique index allows one `published` version per season (hand-written SQL). Placements are never updated; a change is a new version. Superseded versions stay readable. |
| D-11 | Slot uniqueness | **The database refuses two games in one slot within a version.** | Unique (versionId, fieldSlotId) and unique (versionId, gameId). App code writes and maps the unique violation; it does not check-then-write. This is reuse of the Bookable/Reserve lesson, not a new one. |
| D-12 | Reschedule | **Minimal perturbation: only displaced games move.** | Tested game by game. "Regenerate the rest of the season" is a different action with its own warning (RAIN-05). |
| D-13 | Standings and results | **Results are append-only; standings are computed on read.** | A correction is a new `GameResult` row with `supersedesId`. No rank or total is stored as truth. A cache is allowed only with a verify path that recomputes and compares. |
| D-14 | Tiebreak chain | **An ordered list of steps in season settings. Not a rules engine.** | Five metrics, two scopes, restart or continue. Tied-scope steps are skipped until the group is balanced. An unbreakable tie is a shared rank until a commissioner records a decision. The system never draws at random. The config is versioned on the season. |
| D-15 | Brackets | **Single elimination, standard seeding, byes to top seeds.** | Seeding is a frozen snapshot with the standings fingerprint it came from. No ties. A result can be corrected until the next game in its line is played. Double elimination is P2. |
| D-16 | Who signs in | **League staff only.** | Commissioner = org owner or admin. Scorekeeper = org member, limited to results. Coaches, players and the public read public pages with no account. Use the foundation's authorization path; add permissions there the way the template documents, not ad hoc checks. |
| D-17 | Where generation runs | **Synchronously in a server action, with caps.** | At most 16 teams per division, 200 games per season, `maxIterations` ≤ 10,000. Basis: spec 01 §8. No job queue. If a real run in this repo exceeds 5 s, stop and raise it rather than adding infrastructure. |
| D-18 | Notices | **Through the foundation's notifications outbox, on publish only.** | Without provider keys every message is captured in the database. Declare the module required if code outside the marked lines imports it (`src/app/required-modules.ts`). |
| D-19 | Backlog ids | **`L-` numbers, continuous, never reused.** | Commits are `L-006: repair loop`. |
| D-20 | Pending suites | **The engine's suites ship as `tests/unit/league-*.pending.ts`.** | Vitest only collects `*.test.ts`, so CI stays green. An item starts by renaming its suite to `.test.ts` and watching it fail with `NotImplementedError`; it ends with that suite green. Do not weaken an assertion to pass it; if a fixture looks wrong, stop and raise it. |
| D-21 | Unplaced pinned game | **Listed as unplaced only; it does not score `PIN_MOVED`.** | `PIN_MOVED` is for a pinned game sitting in some other slot. A pinned game with no assignment entry is unplaced, which already blocks publishing, and D-9 keeps "unplaced" from ever being a hard violation. Decided by the owner at L-005 (2026-10-08). |
| D-22 | Manual tie resolutions | **The last logged decision listing exactly a group's teams wins; notes carry team ids.** | `manualResolutions` is read as an append-only log, so a correction is appended, never edited (as D-13). An entry listing any other set of teams does not apply. `StandingsRow.note` names teams by id because the engine has only ids; the screen swaps in names. A result naming a team outside `teams` is dropped for both sides. Confirmed by the owner in the L-008 restatement (2026-10-08). |
| D-23 | Rainout and the past | **The caller keeps past open slots out of the reschedule inventory; the engine has no clock.** | `reschedule` offers every free slot in the inventory, so an open slot before the rain day would be taken as a makeup (seen at L-010: a game rained out of Thu Apr 15 moved to Tue Apr 13). The caller drops open slots on or before the cut-off day and keeps every slot that holds a game. The capstone uses the rain day as the cut-off; L-017 uses today from the injected clock. Taken as the default at L-010 (2026-10-08) where the spec is silent; the owner confirms or replaces it at L-017. **Confirmed by the owner 2026-10-12; do not re-open.** |
| D-24 | Engine slot ids | **The loader builds the engine's slot id as `day\|start\|fieldId`, never the row's UUID.** | `reschedule` orders displaced games by old slot id (open since L-007), which is calendar order only for ids of this shape. Unique (seasonId, day, start, fieldId) on `FieldSlot` makes the id one-to-one with the row inside a season, so no column is added. The loader lands with the first screen that calls the engine (L-013). Taken as a default at L-011 and shown to the owner in the plan (2026-10-08). |
| D-25 | Append-only and cascades | **The append-only triggers refuse a direct UPDATE or DELETE and let a foreign-key cascade through.** | `GameResult` and `TieResolution` share one trigger function; it returns early when `TG_OP = 'DELETE'` and `pg_trigger_depth() > 1`, which is true only inside a referential-integrity trigger. Without it the template's delete-org route fails for any org with a recorded score. `AuditEvent` needs no such line because it has no foreign keys. Chosen by the owner at L-011 (2026-10-08) over a strict trigger and over dropping the foreign keys. |
| D-26 | Constraints beyond §8 | **The database also enforces the result chain, pin and playoff slots, same-season joins and value shapes.** | One original result per game (partial unique), a result superseded at most once, and a correction must name a result of the same game: one linear chain, one current result. Unique `Pin.fieldSlotId`, `BracketGame.fieldSlotId` and `Bracket.divisionId` (regenerating a bracket deletes and recreates it). `Pin` and `Placement` carry `seasonId` with composite foreign keys, so a placement cannot join a version, game and slot from different seasons; `Team` carries `seasonId` for its unique name. CHECKs: day and time shape (CHAR(n) pads a short value rather than refusing it), legs, weekday, runs ≥ 0, home ≠ away, seed in uint32. `Season.status` is `setup` / `active` / `closed`. Chosen by the owner at L-011 (2026-10-08). |
| D-27 | Who may edit setup | **Season setup actions require `org.update` (owner and admin); no template edit.** | D-16 says commissioner = owner or admin, which `org.update` already is, so `src/core/authz/permissions.ts` stays untouched. The scorekeeper (org member, results only) needs a permission a member does not hold; that is a template-owned edit, so it is raised at L-015 rather than worked around here. Taken as a default at L-012. |
| D-28 | Generation console storage | **A run stores what the schema already has: the before-repair score rides inside `ScheduleVersion.report`, and `Game` rows are created at the first generation.** | `report` is the stored assignment's `ScoreReport` plus `before: { hardCount, unplaced, softCost }`, so the screen shows before and after with no new column. `Game` rows are written with `skipDuplicates` on (seasonId, key) inside the generating transaction; the engine input is always rebuilt from the current teams, so a team added after a first run changes the pairings of later runs while stored rows keep their first home/away (revisit before L-014 compares versions). A blank seed picks `randomInt(2^32)` in the action, never in the engine. Pins are not loaded yet; L-014 adds them to `buildInput`. |
| D-29 | Compare and pins | **Compare is by game key and slot identity: a game is "changed" when its stored placement differs, and a game placed in only one version shows as from or to "not placed". A pin is one `Pin` row; its legality is `scoreSchedule` over the existing pins plus the new one.** | Home and away come from the stored `Game` row (D-28), so compare shows who hosts as first stored, not as a later run would pair. A pin applies to the next generation; versions already made are never touched (D-10). Only a draft can be published; there is no republish of a superseded version (not in SCHED-02). Closed slots and games outside the current pairings are refused before scoring. |
| D-30 | Who enters scores | **Score entry requires `org.update` (commissioners) for now; the scorekeeper role waits on a template permission.** | A member holds only `share.create`; a results permission means editing `src/core/authz/permissions.ts`, which this project never does. Chosen by the owner at L-015 (2026-10-12). Restore: when the template gains a results permission, switch `PERM` in `result-actions.ts` and add a member-role test. A correction supersedes the newest row only; runs are stored 0-0 on a forfeit; a tie score is accepted (standings handle it). |
| D-31 | Rainout in the app | **Displaced = in a closed slot with no score. A scored game is never displaced or moved, pins are ignored by a reschedule and removed when their slot closes, a makeup slot may fall after the season's last day, and publish refuses a stale draft.** | A game with a result was played, so its slot stays in the reschedule inventory even when closed. A reschedule ignores pins because no other game moves anyway (D-12) and a displaced game's pin points at a closed slot; closing a slot or a day deletes pins on it, which closes the L-014 gap (a pin to a closed slot became a hard violation at the next generation). Makeup slots may be dated after `lastDay` because a makeup day is often an extra week (the capstone's is). Publish refuses a draft that holds an unplayed game in a slot closed since, or that moves a game scored since, whichever action made the draft. One notice per team per publish, listing each of its changed games (RAIN-04). "Regenerate the rest" passes the played games as pins in the engine input and writes no `Pin` rows; a game without a score counts as not played. Taken as defaults at L-017 (2026-10-12) where the PRD is silent. |
| D-32 | Playoffs in the app | **A bracket is seeded from the standings as they stand, playoff games are placed by the rainout engine into free slots after today, a playoff game is scored only once it has a slot on or before today, and a correction overwrites the bracket row with the old score kept in the audit log.** | Unscored season games do not block seeding: the page counts them and the commissioner decides, since a rained-out game is sometimes never made up; regenerating is open until the first playoff result. The fingerprint covers every row of the division table, so any correction warns, and the warning says whether the qualifying teams or their order would change. Placement passes the games to `reschedule` as displaced games, so legality is `scoreSchedule` against the published season and every other playoff game (D-4), nothing else moves (D-12) and the past is kept out (D-23); the home team given to the engine is the better seed. Rounds follow without a rule of their own: a later game's teams are known only after the earlier games are scored, which needs their day to have come. A slot holding a playoff game is left out of the season generator's inventory. A playoff game in a closed slot with no score shows as needing a slot and is placed again by the same action; `closeDay` is unchanged. `BracketGame` rows are updated in place under a row lock on the bracket, not appended like `GameResult` (D-13 covers season results); no reason is asked for a playoff correction. The engine gained `clearResult`, the function spec 02 §7 implies. Taken as defaults at L-018 (2026-10-12) where the PRD is silent. |
| D-33 | Public pages | **A season is public at `/l/<org slug>/<season id>` once it has a published version; the template's share links are not used.** | PUB-01 asks for a page anyone can read, and a share link is the opposite shape: a secret token with a required expiry (INV-08), registered in `src/core/share/links.ts`, which this project never edits. The route is the clone's own and follows the rest of the share contract (spec §7c): one loader, `loadPublicLeague`, built from projections that start empty and opt each field in; names only, no ids; `force-dynamic`; reads limited per IP with the template's share-read budget (60 per 15 minutes), the only anonymous-read limit the template defines. There is no opt-out switch: a league that publishes a schedule has published it. No published version, an unknown org or season and a malformed id are one 404. The page is indexable and keeps the global Referrer-Policy, since the URL holds no secret. PUB-02's 7 days are 168 hours from `publishedAt`, compared against the version the published one replaced; a game placed for the first time carries no mark. Playoff games appear in the bracket section with their slot, not in the schedule list. Taken as defaults at L-019 (2026-10-12) where the PRD is silent. |
| D-34 | Quality table | **The quality table lives at `/o/<org>/seasons/<id>/quality?v=<n>`, counts against the season as it is now, and reports one floor: forced `REST` violations, by counting.** | Defaults where the PRD is silent (L-020). Cost and violations come from `scoreSchedule` (D-4); games, home and away, start times, fields, rest days and byes are plain counts of the placements and judge nothing. A bye is a Monday-to-Sunday week that has a slot and in which the team has no game. The floor generalises spec 01 §6.4: a team's open days are split into runs shorter than `minRestDays`, and a team needing more game days than it has runs is forced into the difference. Every other soft rule is taken as 0, so it is a lower bound and the page says so; when it is 0 the page says no floor can be counted, not that 0 is reachable. A version is re-scored on read with any since-closed slot it uses added back; if that differs from its stored `report`, the page shows both. |
| D-35 | Demo season | **`seed:bracketry` dates the season around the day it runs, gives teams, divisions and fields fixed ids, and stages the three-way tie wherever in the A Division table it can stand alone.** | Defaults where the PRD is silent (L-021). A score is only accepted for a past day and a reschedule only offers slots after today (D-23), so a season with fixed dates is a working demo for a few weeks and never again; the first day is the first Tuesday on or after 24 days ago, which always shifts by whole weeks. Team ids are the engine's sort keys, so with random ids the same seed gave a different schedule on each run (soft cost 133, then 122); with ids hashed from the names it is 301 before repair and 122 after on every run (D-3). Teams have played different numbers of games mid-season, so three teams level at the very top is often impossible to stage; the seed takes the first trio that have all met and the first score seed that leaves them level with nobody else on their total and no tie needing a commissioner. The season differs from the capstone (two divisions, database ids, moving dates), so it is not merged with `tests/unit/league-fixtures.ts`; the nine team names are shared. The golden-path spec runs the seed as a process, because Playwright's loader cannot import files that import `next/navigation`, and it moves a placed playoff slot's day 70 days back in the test database so the game can be scored: the app has no way to score a future game, by design (D-32). |
| D-36 | Deployment | **Bracketry is not deployed.** | Closure decision (L-022), taken as the default the port table already recorded ("Not deployed (sample project)"). No Vercel project and no Neon project exist (checked 2026-10-12: 0 of the Vercel projects and 0 of 19 Neon projects are named bracketry; the repo has no `.vercel` link). The demo is `docs/DEMO.md` on a laptop, and the exec brief says so in its first block. Reversible: deploying later is a new decision row, and D-37's restore note applies first. |
| D-37 | Cost review at closure | **Nothing bills except CI minutes; nothing to slow down or turn off.** | Reviewed 2026-10-12 (L-022). Crons: `vercel.json` carries the template's hourly `/api/cron`, inert with no deployment: **keep the file as is**. Scheduled GitHub Actions: none (`ci.yml` runs on push and pull request only): **keep**. Database: local Postgres only, no Neon compute: nothing to suspend. Vercel auto-deploys: none, and the `ignoreCommand` is already in `vercel.json`. LLM calls and keys: none in the app. Mail and SMS: no provider keys; notices sit in the outbox (D-18). Storage and paid tiers: none. Baseline: Neon compute 0 and Vercel builds 0 for this project. **Restore note / trigger:** if D-36 is ever reversed, change the cron schedule from `0 * * * *` to daily (`0 9 * * *`) in the same commit that links the project, because an hourly tick wakes a Neon database 24 times a day for a demo (conventions, *Cost review at closure*). |
| D-38 | What-if and clinch | **What-if is a GET form on the commissioner's standings page; clinched and eliminated are measured against a cut line `n` in the query string (default 4), from a best and worst rank on points.** | Defaults where the PRD is silent (L-023, 2026-10-12). The number of qualifying teams is only chosen when a bracket is seeded and is not stored on the season, so the flags cannot read it; the page asks, with the bracket form's own default. The engine returns a rank range per team (spec 02 §8) and the page compares it with `n`, so the cut is not an engine input. Hypothetical scores live in the URL and are never written; a score for a game that already has a result is ignored, and the tie-decision form is hidden while any are in play so a decision cannot be recorded against a table that is not real. Three outcomes per game (ties are legal, ST-7). The public page does not show what-if or flags: its reads share the template's per-IP limit and the enumeration costs about 0.4 s at the limit. |
| D-39 | Calendar feed | **A team's feed is `/l/<org>/<season>/calendar.ics?team=<name>`: the published version's regular-season games, as wall times with the season's `TZID`, each event keyed by a hash of its game id.** | Defaults where the PRD is silent (L-024, 2026-10-12). It follows D-33 in every respect it can: public once a version is published, one 404 for every miss, the same per-IP limit, the team picked by name, playoff games left out as they are from the schedule list. The times are written as `'YYYYMMDD'T'HHMM00'` beside the zone name, so no instant is ever computed (D-6); the file carries no `VTIMEZONE` block and relies on the calendar app knowing IANA names. The event key is a hash because the public projection carries no ids (spec §7c); it stays the same across versions, so a rescheduled game moves in the subscriber's calendar instead of appearing twice. Length is `gameMinutes`. Scores are not in the feed. |
| D-40 | Crossover results | **A crossover result counts in each team's own division table, as an opt-in the season loader always takes. D-22 stays the engine's default.** | Chosen by the owner at L-026 (2026-10-12) over leaving crossover games as exhibitions. `StandingsConfig.countCrossover` makes the table count a result for the one team that is in the list; 'tied'-scope steps still read only the games among the tied teams, so head-to-head is untouched; 'all'-scope steps and the points range include crossover games (spec 02 §9, fixtures CX-1 to CX-3). The flag is passed at the call and never stored with the chain. D-22's two tests are unchanged. |
| D-41 | Crossover shape | **One season setting, `crossoverRounds` (0 to 16): in each round every team of the smaller of two divisions plays one team of the other, for every two divisions, no pair twice.** | Defaults where the PRD is silent (L-026, 2026-10-12; DBL-01 is one line). The pairing is spec 01 §9: the larger division's game counts never differ by more than one, rounds stop when every opponent has been met, the host alternates. Key `X:a~b`. The stored `Game.divisionId` is the home team's division; the engine's `Game.awayDivision` carries the other, and equity counts each side in its own division. Round numbers spread the crossover rounds through the season. No per-pair setting, no "these two divisions only", no chosen crossover week: say so if any is wanted. The public page labels the game "Crossover". |
